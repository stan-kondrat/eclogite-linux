# Nix/nixpkgs/NixOS and GNU Guix: package and system description models (for a JSON build DSL)

Research date: 2026-10-03. Nix manual pages cited are the 2.28 reference manual; nixpkgs/NixOS source excerpts were fetched from `master` on that date; Nix C++ source from tag 2.24.0. Guix manual is the current online HTML manual.

## 1. Nix derivations: what goes into the hash; system, stdenv and CPU microarchitecture

### Takeaway
A Nix derivation is a flat record (`name`, `system`, `builder`, `args`, `env`, `outputs`, `inputDrvs`, `inputSrcs`). Its `.drv` path is a content hash of the ATerm serialization. Input-addressed output paths come from a recursive "hash modulo" that replaces each input `.drv` with that input's own modulo hash, so `system`, the builder, every env var (including flags like `-march`) and the whole transitive input graph (compiler included) end up in the output path. Fixed-output derivations (source fetches) are hashed only by their declared content hash. Floating content-addressed (CA) derivations, which key paths by output content and allow "early cutoff", are still an experimental feature.

### Cited Findings
- Only three attributes are required: `name`, `system`, `builder`. `args` defaults to `[]` and `outputs` to `["out"]`. Paths look like `/nix/store/<hash>-hello.drv` and `/nix/store/<hash>-hello`; each extra output gets a suffix (`-dev`, `-lib`, …) — [Nix manual: Derivations](https://nix.dev/manual/nix/2.28/language/derivations)
- A derivation consists of: name, an inputs specification (store objects needed for the build), an outputs specification, a system type (e.g. `x86_64-linux`), and process-creation fields (builder, args, env). "The canonical encoding for every derivation is the 'ATerm' format", and the serialized `.drv` store object is content-addressed. The manual requires that "all inputs be explicitly collected in the inputs field" — [Nix manual: Store derivation](https://nix.dev/manual/nix/2.28/store/derivation/)
- Input addressing means addressing a store object "by the _way it was made_ rather than _what it is_" — [Nix manual: Input-addressing](https://nix.dev/manual/nix/2.28/store/derivation/outputs/input-address)
- `hashDerivationModulo` (Nix 2.24 source) works like this. For a fixed-output derivation it returns `sha256("fixed:out:" + method/algo + ":" + contentHash + ":" + outPath)`, so the recipe (URL, fetcher) does not reach dependents. For other derivations it recursively computes the modulo hash of each `inputDrv`, substitutes those hashes for the input `.drv` paths, and hashes the unparsed (ATerm) derivation with output paths masked. A dependency on a floating-CA derivation marks the result `Deferred`, meaning its output path is not known until build time — [NixOS/nix derivations.cc @2.24.0](https://raw.githubusercontent.com/NixOS/nix/2.24.0/src/libstore/derivations.cc)
- Fixed-output CA: "the content address of the _fixed_ in advanced by the derivation itself". The build fails if the declared and actual hashes differ. Its purpose is "fetching fixed input data like source code from the network", so changing a URL does not cause a mass rebuild. Floating CA requires `extra-experimental-features = ca-derivations`. For CA outputs, "the outputs' store path only depends on the derivation's name, data, and the `method`" — [Nix manual: Content-addressing derivation outputs](https://nix.dev/manual/nix/2.28/store/derivation/outputs/content-address)
- CA derivations shipped in a released Nix (2.4) but are still experimental and opt-in per derivation (`__contentAddressed = true`). A "ca-derivations stabilisation" milestone is open on NixOS/nix, with issues filed as recently as January 2025 (e.g. renaming "realisation" to "build trace") — [NixOS/nix milestone 35](https://github.com/NixOS/nix/milestone/35); [NixOS Wiki: Ca-derivations](https://nixos.wiki/wiki/Ca-derivations)
- Input addressing is "pessimistic": "any minor change (even a comment!) to any of the dependencies causes the _whole graph of descendants to rebuild_". CA gives early cutoff ("If your dependencies have not changed at all (bit-for-bit), you can avoid rebuilding yourself") but depends on bit-reproducible builds. Without them, several CA paths can exist for one derivation — [F. Zakaria, "Demystifying Nix's Intensional Model", 2025-03-08](https://fzakaria.com/2025/03/08/demystifying-nix-s-intensional-model)
- **CPU microarchitecture in nixpkgs**: the platform record has `gcc.arch` / `gcc.tune`. The cc-wrapper (the stdenv compiler wrapper) builds `machineFlags` that include `"-march=${targetPlatform.gcc.arch}"` when `targetPlatform ? gcc.arch` and the compiler supports it (e.g. `x86-64-v2` requires GCC ≥ 11). There is also an `isGccTuneSupported` check for `-mtune` — [nixpkgs cc-wrapper/default.nix](https://raw.githubusercontent.com/NixOS/nixpkgs/master/pkgs/build-support/cc-wrapper/default.nix)
- `make-derivation.nix` defines `gccArchFeature = [ "gccarch-${buildPlatform.gcc.arch}" ]` and appends it to `requiredSystemFeatures`. Only builders that advertise the matching feature will run those builds — [nixpkgs stdenv/generic/make-derivation.nix](https://raw.githubusercontent.com/NixOS/nixpkgs/master/pkgs/stdenv/generic/make-derivation.nix)
- User-facing NixOS config: `nixpkgs.hostPlatform = { system = "x86_64-linux"; gcc.arch = "x86-64-v3"; };` plus `nix.settings.system-features = [ "gccarch-x86-64-v3" ];`. Users report system-features errors when the feature is missing, and recommend trying `nix build` with `--keep-going` before running `nixos-rebuild switch` — [NixOS Discourse #62591](https://discourse.nixos.org/t/nixos-rebuild-system-features-error-when-recompiling-everything-with-gcc-arch-set/62591); [Discourse #51314](https://discourse.nixos.org/t/setting-nixpkgs-hostplatform-gcc-arch-makes-nixos-rebuild-fail/51314)
- Setting `gcc.arch`/`gcc.tune` does not silently override other package attributes. One user who suspected it did found the real cause was slow rebuilds of the whole system — [Discourse #56809](https://discourse.nixos.org/t/nixpkgs-hostplatform-gcc-arch-and-tune-overrides-more-than-youd-expect/56809)

### Inferences
- `gcc.arch` changes the wrapped compiler derivation (cc-wrapper bakes in `-march`) and adds `requiredSystemFeatures`. By the modulo-hash rule, every derivation built with that stdenv therefore gets a new output path. The result is a full-system rebuild with no hits in the public binary cache, which explains the user reports. Nix has no selective, Guix-style "tunable" list.
- `system` is a top-level derivation field and is hashed directly. The stdenv/compiler enters the hash through `inputDrvs` (transitively, all the way down to the bootstrap). Per-package `NIX_CFLAGS_COMPILE` is just an env var in the derivation, so it changes only that package's hash and its dependents' hashes.
- **Borrow:** (a) an explicit, canonical serialized "build recipe" record (in your case canonical JSON) whose hash is the cache key; (b) source fetches keyed purely by content hash (fixed-output), so mirror/URL changes don't invalidate builds; (c) recursive keying, where a package's key includes its dependencies' *keys*, not their full recipes (this is the "modulo" trick); (d) treat target arch/microarch (`x86_64`, `x86-64-v3`) as a top-level hashed field, plus a builder-capability check like `gccarch-*`.
- **Consider:** optional early cutoff by output content hash (a CA-like scheme). It only pays off if builds are bit-reproducible; Nix has kept it experimental for more than 4 years. A simpler design is to use input-addressed keys, and additionally record each output's content hash in the lock file for verification and dedup.

- Exact nixpkgs version in which `gccarch-*` `requiredSystemFeatures` was introduced was not found. The source comment says it is still platform-conditional ("TODO: remove platform condition").

## 2. callPackage, override/overrideAttrs, overlays, feature flags, combinatorial explosion

### Takeaway
nixpkgs packages are functions whose named arguments are dependencies and feature flags (`withX ? false`). `callPackage` fills these arguments from the package set, which is name-based dependency injection. `.override` changes the arguments, `.overrideAttrs` changes the `mkDerivation` attributes, and overlays (`final: prev: {…}`) replace attributes in the global fixpoint, so every consumer sees the change. Flags do not propagate on their own; only replacing an attribute in the package set (via an overlay) affects dependents.

### Cited Findings
- "For every attribute in the function's argument, `callPackage` passes an attribute from the `pkgs` attribute set if it exists." Explicit args take precedence: `pkgs.callPackage ./hello.nix { audience = "people"; }`. Post-hoc: `hello.override { audience = "folks"; }` — [nix.dev callPackage tutorial](https://nix.dev/tutorials/callpackage)
- `.override` "is used to override the arguments passed to a function", e.g. `pkgs.foo.override (previous: { arg1 = previous.arg1; })`. `.overrideAttrs` overrides "the attribute set passed to a `stdenv.mkDerivation` call", e.g. `pkgs.hello.overrideAttrs (finalAttrs: previousAttrs: { pname = previousAttrs.pname + "-bar"; })`. `overrideDerivation` is low-level ("You should prefer `overrideAttrs` in almost all cases") — [nixpkgs manual: Overriding](https://ryantm.github.io/nixpkgs/using/overrides/)
- Overlays are "Nix functions which accept two arguments, conventionally called either final and prev". Use `final` for dependencies and `prev` for the thing being replaced. Overlays "are applied in order". Example: `blas = prev.blas.override { blasProvider = final.mkl; };` — [nixpkgs manual: Overlays](https://ryantm.github.io/nixpkgs/using/overlays/)
- Real feature-flag arguments from emacs's `make-emacs.nix`: `withAcl ? false`, `withCairo ? withX`, `withDbus ? stdenv.hostPlatform.isLinux`, `withGTK3 ? withPgtk && !noGui`, `withNativeCompilation ? stdenv.buildPlatform.canExecute stdenv.hostPlatform`. Defaults can be computed from other flags or from the platform — [nixpkgs make-emacs.nix](https://raw.githubusercontent.com/NixOS/nixpkgs/master/pkgs/applications/editors/emacs/make-emacs.nix)

### Inferences
- nixpkgs avoids combinatorial explosion by convention: each attribute has one default variant, and only the attributes that exist in the package set (defaults plus a few named variants like `emacs-nox`) are built by Hydra and cached. Any `.override` produces a new hash that you build yourself. I found no single primary doc stating this policy (see Gaps).
- No global USE-flag propagation: `withX11` on package A doesn't affect B unless an overlay replaces B in the fixpoint. That gives local reasoning, but "turn X11 off everywhere" requires editing many packages.
- **Borrow:** package = `{ deps by name, flags with defaults, build attrs }`; per-VM config overrides flags per package; a single "overlay-like" layer where a VM can replace a package for all consumers (e.g. `"replace": {"openssl": "libressl"}`), applied in a defined order.
- **Avoid:** three overlapping override mechanisms (`override`/`overrideAttrs`/`overrideDerivation`) and the lazy fixpoint (`final`/`prev` confusion). In JSON, use one merge model: flags plus attr patches, merged deterministically. Keep flag defaults as literals or a tiny expression subset (e.g. `"default": {"if": "arch==x86_64"}`) rather than arbitrary code.

### Gaps
- No primary source found stating Hydra's exact policy (only top-level attrs with `hydraPlatforms`/`meta` are built), so the "binary cache only for defaults" point is inference.

## 3. NixOS module system (options, types, priorities, kernel config, closure, stateVersion, generations)

### Takeaway
NixOS config is a set of modules. Each module declares typed `options` and sets `config` values, and pulls in other modules via `imports`. All definitions of an option are merged according to its type, and numeric priorities resolve conflicts. One `configuration.nix` drives kernel config, packages and services. The evaluated config is built into a single toplevel system derivation whose closure forms one "generation".

### Cited Findings
- Module shape: `{ config, pkgs, ... }: { imports = [ ./vpn.nix ]; options… ; config… }`. Options are declared with `mkOption { type = types.bool; default = false; description = …; }`. There are `mkIf`/`mkMerge` and `mkBefore`/`mkAfter` for list ordering — [NixOS manual: Writing modules](https://nixos.org/manual/nixos/stable/#sec-writing-modules)
- Numeric priorities in `lib/modules.nix` (lower number wins): `mkOptionDefault = mkOverride 1500`, `mkDefault = mkOverride 1000`, `defaultOverridePriority = 100` (a plain definition), `mkImageMediaOverride = mkOverride 60`, `mkForce = mkOverride 50`, `mkVMOverride = mkOverride 10`; `defaultOrderPriority = 1000` for mkBefore/mkAfter ordering — [nixpkgs lib/modules.nix](https://raw.githubusercontent.com/NixOS/nixpkgs/master/lib/modules.nix)
- Kernel config is set through `boot.kernelPatches`, a list of `{ name; patch; structuredExtraConfig; }`. `patch` can be `null` for config-only changes. Keys have no `CONFIG_` prefix and values are `lib.kernel.yes|no|module` — [NixOS Wiki: Linux kernel](https://wiki.nixos.org/wiki/Linux_kernel)
- nixpkgs' own `common-config.nix` uses the same structured form with version guards: `DEBUG_INFO = yes; DEBUG_INFO_BTF = whenAtLeast "5.11" (option yes); DEBUG_INFO_REDUCED = whenAtLeast "5.13" (option no);` (`option` = "set if the symbol exists, don't fail otherwise") — [nixpkgs common-config.nix](https://raw.githubusercontent.com/NixOS/nixpkgs/master/pkgs/os-specific/linux/kernel/common-config.nix)
- `system.stateVersion` "defines the first version of NixOS you have installed on this particular machine, and is used to maintain compatibility with application data (e.g. databases) created on older NixOS versions". It makes default package versions for stateful services depend on that first version. "Most users should **never** change this value after the initial install". If unset, Nix warns and defaults to the current release — [nixpkgs nixos/modules/misc/version.nix](https://raw.githubusercontent.com/NixOS/nixpkgs/master/nixos/modules/misc/version.nix)

### Inferences
- **Borrow:** (a) typed option schema per "module" (you can use JSON Schema) with defaults; (b) a small fixed priority ladder (`default` < normal < `force`) to resolve conflicts between a base profile and a per-VM config; (c) kernel config as a structured map `{ "DEBUG_INFO": "y", "BTF": {"value":"y","optional":true,"minVersion":"5.11"} }` merged over a base config, with an "optional" marker for symbols that may not exist in the pinned kernel version; (d) a `stateVersion`-like field that records the schema/data version a VM image was first created with, so later defaults don't break persistent disks.
- **Avoid:** modules that can read the *final* merged config (`config.*`) while also defining it. This lazy fixpoint drives NixOS's power and its infinite-recursion errors. A JSON system can merge layers in a fixed order (base → profile → VM) and then validate the result, with no self-reference.
- Generations/rollback: NixOS keeps each built system as a numbered profile generation and lets you boot an older one. For VMs, the equivalent is keeping previous root-image hashes plus their lock files.

### Gaps
- Did not fetch the NixOS manual text on generations or `nixos-rebuild` rollback (the options page exceeded the fetch size limit). The generations description above is general knowledge and not directly cited here; Guix's equivalent is cited in section 5.

## 4. Flakes: inputs and flake.lock

### Takeaway
`flake.lock` is a JSON graph. Each node maps an input's `original` (unlocked) reference to a `locked` reference that includes the git `rev`, a `narHash` (SRI sha256 of the source tree's NAR serialization), `lastModified` and (for non-GitHub git) `revCount`. Inputs can share a node through `follows`.

### Cited Findings
- `flake.lock` is "a UTF-8 JSON file" that "contains a graph structure isomorphic to the graph of dependencies of the root flake". Each node has `inputs` (name → node label), `original`, `locked` and `flake` (bool), and there is a `root` node. Locked fields: `narHash` (SRI SHA-256 of the NAR), `rev`, `lastModified` (commit time, Unix seconds), `revCount` (not available for GitHub), and `type`/`owner`/`repo`. `follows` lets an input reuse another input's node — [Nix manual: nix flake](https://nix.dev/manual/nix/2.28/command-ref/new-cli/nix3-flake)
- Example lock node (version 7):
  ```json
  {"version":7,"root":"n1","nodes":{
    "n1":{"inputs":{"nixpkgs":"n2"}},
    "n2":{"locked":{"owner":"edolstra","repo":"nixpkgs",
      "rev":"7f8d4b088e2df7fdb6b513bc2d6941f1d422a013","type":"github",
      "lastModified":1580555482,
      "narHash":"sha256-OnpEWzNxF/AU4KlqBXM2s5PWvfI5/BS6xQrPvkF5tO8="}}}}
  ```
  — [Nix manual: nix flake](https://nix.dev/manual/nix/2.28/command-ref/new-cli/nix3-flake)

### Inferences
- **Borrow directly:** a lock file that stores both the git `rev` and a content hash of the *checked-out tree* (`narHash`-like, e.g. sha256 of a deterministic tar or a git tree hash). The rev gives provenance; the tree hash lets you verify mirrors or tarballs and makes the source a fixed-output input. Keep `original` (what the config asked for, e.g. a branch) next to `locked`, so "update" can re-resolve. Record `lastModified` for human-readable ordering and for SOURCE_DATE_EPOCH-style reproducibility.
- **Borrow:** a flat `nodes` map keyed by label, plus `follows`-style dedup, so one glibc/gcc pin is shared by all packages.
- **Avoid:** nesting of lock files (each flake has its own lock graph) and the flake/non-flake distinction. A single repo-wide lock per VM is simpler.

### Gaps
- Flakes' experimental status in 2025–2026 was not checked against a primary source.

## 5. Guix: package records, transformations, --tune, channels, time-machine, guix system, grafts

### Takeaway
Guix packages are Scheme records (`name`, `version`, `source` origin with mandatory sha256, `build-system`, `arguments`, `inputs`/`native-inputs`/`propagated-inputs`, `properties`, `replacement`). They are lowered to the same kind of derivation as Nix. Variants are made by inheriting a record or by graph rewriting (`package-input-rewriting`, `package-mapping`), and the same rewrites are exposed as CLI transformation options. `--tune` is selective: only packages marked `tunable?` are rebuilt with a `-march` compiler wrapper, and the tuned build is grafted in as a `replacement`, so dependents are not rebuilt. Reproducibility comes from channels pinned by commit, replayed with `guix time-machine`.

### Cited Findings
- Package example: `(package (name "hello") (version "2.10") (source (origin (method url-fetch) (uri …) (sha256 (base32 "0ssi…"))))) (build-system gnu-build-system) (arguments (list #:configure-flags #~(list "--enable-silent-rules"))) (inputs (list gawk)) …)`. The `sha256` "is mandatory". `package-derivation` lowers a package plus a target system to a `.drv`; `package-cross-derivation` does the same for cross builds — [Guix manual: Defining Packages](https://guix.gnu.org/manual/en/html_node/Defining-Packages.html)
- `inputs` are runtime dependencies built for the target. `native-inputs` are build-time tools for the build machine ("such as Autoconf, Automake, pkg-config, Gettext, or Bison"). `propagated-inputs` are installed alongside, e.g. a C library whose headers another library needs, or languages without a runtime search path. `arguments` are keyword args to the build system (`#:tests?`, `#:configure-flags`, `#:make-flags`, `#:phases`). `outputs` defaults to `'("out")`. `replacement` (default `#f`) is used for grafts — [Guix manual: package Reference](https://guix.gnu.org/manual/en/html_node/package-Reference.html)
- Variants: `(package (inherit hello) (version "2.2") (source …))`, `(modify-inputs (package-inputs gdb) (delete "guile"))` (also prepend/append/replace), `package-input-rewriting` (list of package → replacement pairs), and `package-mapping`. `#:deep? #t` also rewrites implicit inputs; `options->transformation` turns CLI options into a procedure — [Guix manual: Defining Package Variants](https://guix.gnu.org/manual/en/html_node/Defining-Package-Variants.html)
- Transformation options: `--with-input=package=replacement` ("recursive and deep"), `--with-source=[package[@version]=]source`, `--with-commit=package=commit` (SHA1, tag or `git describe`), `--with-branch=package=branch`, `--with-patch=package=file` (applied with the origin's default `-p1`; e.g. `guix build coreutils --with-patch=glibc=./glibc-frob.patch` rebuilds the whole graph), `--with-configure-flag=package=flag`, `--with-c-toolchain=package=toolchain` (with an ABI warning), and `--without-tests=package` (which "Changes the store hash, requiring rebuilds of all dependents") — [Guix manual: Package Transformation Options](https://guix.gnu.org/manual/en/html_node/Package-Transformation-Options.html)
- `--tune[=cpu]` applies `-march=CPU` only to packages with `(properties '((tunable? . #t)))`, and detects the host CPU when no CPU is given. "Tuned packages are grafted onto dependents to minimize rebuilds"; `--no-grafts` cancels the effect, and tests are skipped. The main benefit is for programs that use SIMD and lack runtime dispatch — [Guix manual: Package Transformation Options](https://guix.gnu.org/manual/en/html_node/Package-Transformation-Options.html)
- `--tune` blog post (Ludovic Courtès, Guix-HPC, 2022-01-06): host CPU detection is "inspired by that used by GCC's `-march=native`". Compiler packages carry metadata listing the CPU names they recognize, which gives good error messages. Selective tuning avoids "rebuilding packages that could not possibly benefit". Transformations are recorded in manifests and replayable, and the build farm pre-builds tuned variants as substitutes — [Guix-HPC blog: Tuning packages for a CPU micro-architecture](https://hpc.guix.info/blog/2022/01/tuning-packages-for-a-cpu-micro-architecture/)
- Implementation (`guix/transformations.scm`): `tuned-package` inherits the package and swaps its build system for `build-system-with-tuning-compiler`. That wrapper prepends a `"tuning-compiler"` (a `-march` wrapper) to the build inputs, after checking the compiler's `compiler-cpu-architectures` property. It also sets `#:tests? #f` and adds the property `(cpu-tuning . ,micro-architecture)`. `package-tuning` maps over the graph with `package-mapping … #:deep? #t` and, for each `tunable?` package, returns the original with `(replacement (tuned-package p micro-architecture))` — [Guix transformations.scm](https://codeberg.org/guix/guix/raw/branch/master/guix/transformations.scm)
- Grafts: with a `replacement`, dependents are "rewritten" to refer to the replacement instead of being rebuilt. Constraints: the name+version length must equal the original's, and shared libraries need the same SONAME and ABI. Grafting cost scales with package size and is typically under a minute, which is orders of magnitude cheaper than a rebuild. `guix build bash --no-grafts` gives the ungrafted build — [Guix manual: Security Updates](https://guix.gnu.org/manual/en/html_node/Security-Updates.html)
- Channels pinned by commit: `guix describe -f channels > channels.scm` produces `(list (channel (name 'guix) (url "https://git.guix.gnu.org/guix.git") (commit "6298c3ff…")) …)`. `guix time-machine -C channels.scm -- shell python -- python3` "will always fetch the exact same Guix instance". Pinning covers the whole package set and the tools — [Guix manual: Replicating Guix](https://guix.gnu.org/manual/en/html_node/Replicating-Guix.html)
- `guix system`: one `(operating-system (host-name …) (bootloader …) (file-systems (cons … %base-file-systems)) (packages (cons screen %base-packages)) (services (append (list (service openssh-service-type …)) %base-services)))`. `modify-services` tweaks base services with `(inherit config)`. `guix system reconfigure|build|image` applies, builds or produces a disk image. Each reconfigure creates a generation that can be rolled back, and the manual notes you should "never have to touch files in /etc" — [Guix manual: Using the Configuration System](https://guix.gnu.org/manual/en/html_node/Using-the-Configuration-System.html)

### Inferences
- **Store hash effect of `--tune`:** the tuned package gets a *new* derivation and store path, because the tuning-compiler wrapper is an extra build input and the properties change. Dependents keep their original derivations and are grafted, i.e. their references are rewritten after the build. Your system has no `/nix/store` paths to rewrite, so grafting is unnecessary: if packages install to `/usr` and link via SONAME, a tuned `libfoo.so` can be swapped into the root image without rebuilding dependents, as long as the ABI is the same. Model this as "package key changes; dependents' keys don't" for packages flagged `tunable` (an explicit ABI-stable boundary).
- **Borrow:** (a) the `inputs` / `native-inputs` / `propagated-inputs` split. For a /usr-composed image this maps to runtime deps (go in the image), build-only deps (not in the image), and deps that must be in the image whenever this package is; (b) a `tunable: true` property plus per-VM `cpu: "x86-64-v3"`, applied only to whitelisted packages (glibc string functions already dispatch at runtime; things like zstd, xz and openssl may benefit); (c) compiler metadata listing the `-march` values it supports, used to validate configs; (d) transformation options as *data*, e.g. `{"withCommit": {"glibc": "abc123"}, "withPatch": {"glibc": ["fix.patch"]}, "withConfigureFlag": {...}, "withoutTests": ["python"]}`. These map almost one-to-one onto JSON fields in a per-VM config and are recorded in the lock; (e) `channels.scm` with pinned commits plus a time-machine equivalent: the lock pins the *recipe repo* commit as well as each upstream source commit; (f) `operating-system` with `%base-*` lists extended by the VM, and `modify-services` with `inherit` for service config.
- **Avoid:** grafts' fragile equal-length string constraint (not needed without a store), and deep-by-default rewriting that silently rebuilds the world (`--with-patch=glibc` rebuilds everything). Make the rebuild scope explicit and visible in the lock diff.

### Gaps
- I did not verify which packages in current Guix carry `tunable? #t`, or whether the build farm still publishes tuned substitutes in 2026.

## 6. Known pain points and criticisms a simpler JSON design should avoid

### Takeaway
The documented costs are: evaluation that can block on builds (IFD) and is sequential; whole-graph rebuilds from input addressing (and from global microarch flags); the long-experimental status of CA early cutoff; lazy fixpoint complexity (overlays and modules); and multiple overlapping override APIs. A static JSON recipe graph with no evaluation-time builds avoids most of these by construction.

### Cited Findings
- IFD happens when an evaluated store path is passed to `import`, `builtins.readFile`, `builtins.readDir`, etc. "Evaluation can only finish when all required store objects are realised", and "Since the Nix language evaluator is sequential, it only finds store paths to read from one at a time", which is much slower. With `allow-import-from-derivation = false`, "it is ensured that evaluation is complete and Nix can produce a build plan before starting any realisation" — [Nix manual: Import From Derivation](https://nix.dev/manual/nix/2.28/language/import-from-derivation)
- Input-addressed rebuild cascades ("even a comment") and the reproducibility requirement for CA — [Zakaria 2025](https://fzakaria.com/2025/03/08/demystifying-nix-s-intensional-model)
- CA derivations are still experimental years after shipping in Nix 2.4, with a stabilisation milestone open — [NixOS/nix milestone 35](https://github.com/NixOS/nix/milestone/35)
- Setting a global `gcc.arch` leads to system-features build errors and forces local rebuilds of everything — [Discourse #62591](https://discourse.nixos.org/t/nixos-rebuild-system-features-error-when-recompiling-everything-with-gcc-arch-set/62591); [nixpkgs issue #227501 "Configuration evaluation fails with gcc.arch set"](https://github.com/NixOS/nixpkgs/issues/227501)
- `overrideDerivation` pitfall: "A package's attributes are evaluated _before_ being modified", so you should prefer `overrideAttrs` — [nixpkgs manual: Overriding](https://ryantm.github.io/nixpkgs/using/overrides/)
- An April 2026 literature review ("Nix: A Solution With Problems", M. Zwinger, arXiv 2604.11398, revised 2026-07-10) identifies trust and granular incremental builds as old problems Nix has not solved, and says Nix "does introduce some novel problems of its own" — [arXiv 2604.11398](https://arxiv.org/abs/2604.11398)
- Guix grafting constraints (equal name-length, same SONAME/ABI) and the side effects of `--tune` (tests skipped) — [Guix manual: Security Updates](https://guix.gnu.org/manual/en/html_node/Security-Updates.html); [Guix manual: Package Transformation Options](https://guix.gnu.org/manual/en/html_node/Package-Transformation-Options.html)

### Inferences
- Design rules that follow for a JSON system:
  1. The recipe graph is static data. It is resolved *before* any build: no build outputs may be read during resolution (no IFD), so a full build plan plus cache-key list can always be printed from config + lock.
  2. Use one merge algorithm with a fixed layer order and 2–3 priorities. No self-referential fixpoint, and no turing-complete expressions in recipes (keep build logic in shell build scripts that are hashed as inputs).
  3. Cache key = sha256(canonical JSON of {recipe, source tree hash, arch, cpu level (only if the package is tunable or the global baseline changes), flags, toolchain key, dependency keys}). Use dependency *keys*, not recipes (modulo-style). Record output content hashes in the lock to allow optional early cutoff later.
  4. Make the rebuild scope explicit: `cpu` baseline is global (changes everything), `tune` is per-package and ABI-preserving (changes only that package). Show "N packages will rebuild" from a lock diff.
  5. Pin both the recipe repo commit and each upstream git rev plus tree hash, like flake.lock and Guix channels.
- I found no primary-source survey on Nix language learning curve or nixpkgs evaluation time/memory. These are widely discussed in the community but are not cited here.
