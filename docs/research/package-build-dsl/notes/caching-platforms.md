# Content-addressed build caching and platform modeling (Bazel, Buck2, BuildKit, Yocto sstate, Nix) — lessons for a JSON build DSL

Scope: how mature build systems compute cache keys, model target platforms/toolchains, and avoid both spurious misses and incorrect hits. Target use: a single-user, AI-maintained, source-built rolling Linux (linux-libre, glibc, GNU userland) for VMs; builds pinned to git commits; cache keyed by hash of all inputs; arm64/x86_64 and x86-64-v1/v3 must yield distinct entries. Research date: 2026-10-03. Tool-call budget limited; where primary docs were truncated or not fetched, this is flagged in Gaps.

## Bazel: action keys, remote/disk cache, configurations, platforms, toolchains, hermeticity

### Takeaway
Bazel caches per *action*: key = digest of (Command proto: argv + sorted env + output paths + working dir) + digest of the input-root Merkle tree + platform properties + optional salt; results go to an Action Cache (AC) mapping action-hash -> result metadata, with file bytes in a Content-Addressable Store (CAS). Platforms are sets of `constraint_value`s; toolchains are selected by matching constraints. Configuration (flags, target platform) leaks into output paths (`k8-fastbuild-ST-<hash>`), which in turn leaks into command lines and therefore cache keys — the "configuration explosion" / path-mapping problem. Anything not declared (host compilers, `$PATH`) is invisible to the key and causes *incorrect* hits.

### Cited Findings
- Remote cache stores two kinds of data: an Action Cache, "a map of action hashes to action result metadata", and a CAS of output files; over HTTP these live under `/ac/` and `/cas/`. — [Bazel: Remote Caching](https://bazel.build/remote/caching)
- "Each action has inputs, output names, a command line, and environment variables. Required inputs and expected outputs are declared explicitly for each action." Only env vars allowlisted via `--action_env` are part of the action definition. — [Bazel: Remote Caching](https://bazel.build/remote/caching)
- Local disk cache: `--disk_cache=path`; since Bazel 7.4 GC via `--experimental_disk_cache_gc_max_size` / `--experimental_disk_cache_gc_max_age`. — [Bazel: Remote Caching](https://bazel.build/remote/caching)
- Hermeticity pitfalls named by the docs: (1) environments with different `$PATH` won't share cache hits; (2) "Bazel currently does not track tools outside a workspace ... two users with different compilers installed will wrongly share cache hits"; (3) an input modified during a build can cause invalid results to be uploaded. — [Bazel: Remote Caching](https://bazel.build/remote/caching)
- REAPI `Action` fields: `command_digest`, `input_root_digest` (Merkle root `Directory`), `timeout`, `do_not_cache`, `salt` ("used to place this Action into a separate cache namespace"), `platform`. `Command`: `arguments`, `environment_variables` (must be lexicographically sorted by name), `output_paths`, `working_directory`. Platform properties are sorted by name then value and are "implicitly part of the action digest, so even tiny changes in the names or values (like changing case) may result in different action cache entries." — [remote_execution.proto](https://github.com/bazelbuild/remote-apis/blob/main/build/bazel/remote/execution/v2/remote_execution.proto)
- Platforms: a constraint is a distinguishing property (CPU arch, GPU presence, compiler version); a platform is a collection of constraints. `constraint_setting(name="cpu")`, `constraint_value(name="x86", constraint_setting=":cpu")`, `platform(name="linux_x86", constraint_values=["@platforms//os:linux","@platforms//cpu:x86"])`. Three roles: host (runs Bazel), execution (runs actions), target (where output runs). `--platforms` selects target; default is `@platforms//host` (auto-detected). Standard values like `@platforms//cpu:x86_64`, `@platforms//os:linux` live in github.com/bazelbuild/platforms. — [Bazel: Platforms](https://bazel.build/extending/platforms)
- Toolchain resolution: inputs = required toolchain types, target platform, available exec platforms, registered toolchains. A toolchain's `target_compatible_with`/`exec_compatible_with` matches if every listed constraint_value is present in the platform (extra platform constraints don't block). Steps: filter exec platforms by target's `exec_compatible_with`; drop toolchains whose `target_settings` don't match; per exec platform pick first compatible toolchain per type; drop exec platforms missing a mandatory toolchain; first remaining exec platform wins. Priority: `--extra_toolchains` (last = highest), root module `register_toolchains()`, WORKSPACE, non-root modules, built-in suffix. — [Bazel: Toolchains](https://bazel.build/extending/toolchains)
- Transitions are "a function from an input configuration to one or more output configurations" (1:1 or 1:N split, e.g. multi-arch). Cost: "larger build graphs, less comprehensible build graphs, and slower builds"; a naive transition appending to an `--owner` flag yields 2^n configured targets — "exponentially larger than the target graph". The docs still say "TODO: Add strategies for measurement and mitigation". — [Bazel: Configurations](https://bazel.build/extending/config)
- Output layout: one `bazel-out` subdir per configuration, mnemonic encodes CPU + compilation mode (`k8-fastbuild`, `k8-opt`, `k8-dbg`); configurations with Starlark transitions append `-ST-<hash>`; tools build in an exec config dir (`k8-opt-exec-...`). — [Bazel: Output Directory Layout](https://bazel.build/remote/output-directories)
- Bazel 7 added `diff_against_dynamic_baseline` to `--experimental_output_directory_naming_scheme`, so ST-hash reflects the diff against the top-level config and transitions that return to a previous config get the same path, "improving cache hit rates"; exec dirs became e.g. `k8-opt-exec-ST-011b9bdc32ed`. — [BuildBuddy: What's New in Bazel 7.0](https://www.buildbuddy.io/blog/whats-new-in-bazel-7-0/); [bazel PR #16910](https://github.com/bazelbuild/bazel/pull/16910)
- Path mapping (`--experimental_output_paths=strip`, Bazel >= 7.2): Bazel rewrites config segments out of paths in action command lines so the same compile reached via two configurations gets one cache key; actions opt in via the `supports-path-mapping` execution requirement; only for sandboxed/remote spawns. Reported example: with disk cache, 105.4s -> 26.9s (1,833 hits) vs 92.1s -> 86.7s without the flag. — [bazel Discussion #22658 "The State of Path Mapping"](https://github.com/bazelbuild/bazel/discussions/22658)

### Inferences
- The REAPI split (Command proto + input Merkle root + platform + salt) is a good template for a JSON system: hash a canonical "action/recipe" document separately from a content-hash tree of inputs, and keep a `salt`/`cache_epoch` knob to invalidate a namespace wholesale (e.g. after fixing a non-hermetic bug).
- Bazel's main lesson: config identity must enter the key only through values that actually change the output. Output paths embedding configuration hashes create false misses (ST-hash, path mapping exist to repair this). A small system should use path-independent build dirs (fixed `/build/src`, `/build/out` inside a sandbox/VM) so paths never vary per configuration.
- The "two users with different compilers wrongly share hits" warning is the exact failure mode to avoid: the toolchain must be an *input* (by content hash) rather than an ambient host tool.
- Constraint model fits the user's needs: settings `cpu` {x86_64, aarch64} and `x86_level` {v1,v2,v3,v4}; a platform = {os:linux, libc:glibc, cpu, level}. Toolchains declare `target_compatible_with` and are resolved deterministically (first match in registration order), and the resolved toolchain's *hash*, not its name, enters the key.

### Gaps
- Exact algorithm for the ST-hash (which options are hashed) is described as an undocumented implementation detail; not confirmed in primary docs.
- `--incompatible_strict_action_env` (fixed PATH for actions) is a known mitigation but I did not fetch its doc page in this session.

## Buck2: configurations, platforms, configured-target hashing, execution platforms

### Takeaway
Buck2 uses the same constraint/platform concepts as Bazel but names configurations by a hash of their constraint values ("hashed buck-out"), distinguishes target vs execution platforms, and layers "modifiers" and transitions on top. Execution platforms also carry execution policy (local/remote/hybrid, whether cache upload is allowed).

### Cited Findings
- Configurations model variation in architecture, OS, opt level, compiler, sanitizers, etc.; "the configuration is currently represented as a hash of its values (a 'hashed buck-out')", avoiding path collisions when a target appears in multiple configurations. — [Buck2: Configurations](https://buck2.build/docs/concepts/configurations/)
- Components: enum-like constraint settings/values (e.g. `//config:build_mode[debug]`) and config settings that can reference buckconfig values; `select()` resolves on them ("If multiple conditions match and all matches have the same value, the select() resolves to that value"). — [Buck2: Configurations](https://buck2.build/docs/concepts/configurations/)
- Resolution order: `--target-platforms` flag, else target's `default_target_platform`, else `.buckconfig` default; then configuration modifiers; then transitions for parts of the graph. — [Buck2: Configurations](https://buck2.build/docs/concepts/configurations/)
- "Target platforms are the platforms where your code runs, and execution platforms are the ones used to run compilers and build tools during the build process." — [Buck2: Configurations](https://buck2.build/docs/concepts/configurations/)
- Glossary: configuration = set of constraint values used to resolve `select` before rule evaluation; execution platform includes supported execution types (remote/local/hybrid) and whether cache uploads are supported; transition changes configuration across a dependency edge; "Action digest: Encoded action representation. It is sent to remote execution. Used ... to check for cache hits." — [Buck2: Glossary](https://buck2.build/docs/concepts/glossary/)

### Inferences
- Buck2 shows that naming a configuration by hash-of-values is fine for machines but should be paired with a readable label (Buck2 prints configured targets as `label (cfg-name#hash)`, from my knowledge — unverified here). For a JSON system: `platform_id = "x86_64-v3-linux-gnu"` for humans + `platform_hash` for the key.
- Making "may upload to cache" a property of the execution environment is useful: builds done in a non-hermetic/debug environment should be readable from cache but never written.

### Gaps
- Exact on-disk format of configured target labels/hashes in buck-out not confirmed from fetched docs.

## Dockerfile / BuildKit: LLB, per-instruction cache keys, platforms

### Takeaway
BuildKit converts Dockerfiles into an LLB DAG whose vertices have a definition digest covering all graph definitions up to that vertex; cache keys combine an op's own digest with its inputs' keys, with lazy content-based checksums for file inputs. RUN is keyed purely by command text (+ parent + args/env), not by what it fetches — the classic `apt-get update` stale-cache trap. `--platform`/`TARGETPLATFORM` are build args and so enter the key.

### Cited Findings
- RUN: cache uses only the command string; "the files updated in the container aren't examined to determine if a cache hit exists", so `RUN apt-get -y update` won't be re-run when upstream packages change; force with `--no-cache`, `--no-cache-filter`, or changing a prior layer. — [Docker: Build cache invalidation](https://docs.docker.com/build/cache/invalidation/)
- COPY/ADD: checksums from file content/metadata; "the modification time of a file (mtime) is not taken into account". — [Docker: Build cache invalidation](https://docs.docker.com/build/cache/invalidation/)
- Build args participate in cache checksums; secret *contents* do not, but secret IDs and mount paths do. `SOURCE_DATE_EPOCH` as a build arg: dynamic values (e.g. git timestamps) break cache each build; fixed values preserve reuse. — [Docker: Build cache invalidation](https://docs.docker.com/build/cache/invalidation/)
- Solver: an op's `CacheMap` has a `Digest` (e.g. image manifest digest or git commit SHA for sources); result cached by a checksum combining this digest with input cache keys; `Deps` may carry selectors or content-based cache functions for inputs. Each vertex has a "content-addressable digest representing a checksum of all graph definitions up to that vertex". Content checksums of snapshots are postponed because computing them after every op is too slow; solver prefers definition-based matches and skips content-based checks when possible. — [pkg.go.dev moby/buildkit/solver](https://pkg.go.dev/github.com/moby/buildkit/solver); [BuildKit solver design](https://crazymax.dev/buildkit/design/solver/)
- Multi-platform: `--platform linux/amd64,linux/arm64`; automatic args `BUILDPLATFORM`, `TARGETPLATFORM`, `TARGETOS`, `TARGETARCH` (plus variant); cross-compile pattern `FROM --platform=$BUILDPLATFORM golang:alpine AS build` to avoid QEMU emulation while targeting other arches; QEMU emulation easiest but slow. — [Docker: Multi-platform builds](https://docs.docker.com/build/building/multi-platform/)

### Inferences
- Two-tier keying (cheap definition digest first, expensive content checksum only when needed) is worth copying: hash the JSON recipe + pinned commit IDs first; only hash source trees when a source is a local directory without a commit ID.
- Network-fetching steps must be either (a) fixed-output (expected hash declared, like Nix FODs) or (b) forbidden. Never key a step on a command string that fetches mutable remote state.
- Docker's `FROM --platform=$BUILDPLATFORM` pattern = Bazel's exec vs target split: build-tools run on the host arch, output targets another arch; the key must include *target* platform and the *exec* toolchain hash, but host arch should not matter if cross toolchain output is deterministic (in practice, include it until verified).
- Cache mounts (`RUN --mount=type=cache`) are deliberately outside the key — appropriate for ccache/download caches, dangerous if build output depends on their contents.

### Gaps
- Docker docs on platform variants (`linux/amd64/v3`, `TARGETVARIANT`) and whether amd64/v2/v3 produce distinct cache entries were not covered in the fetched page; `TARGETVARIANT` exists per my knowledge but unverified here.
- Did not fetch the cache-mount doc page.

## Yocto/BitBake sstate: basehash/taskhash, variable dependencies, MACHINE/tune, hash equivalence, diffsigs

### Takeaway
BitBake signs every task: basehash = hash of the task's code plus all variables/functions it (transitively) references, discovered automatically by parsing; taskhash = basehash + taskhashes of dependency tasks. Variables can be excluded globally (`BB_BASEHASH_IGNORE_VARS`: TMPDIR, WORKDIR, DL_DIR, SSTATE_DIR...) or per-variable (`[vardepsexclude]`, `[vardeps]`). Architecture/tune enters via PACKAGE_ARCH/TUNE_PKGARCH, so machines with the same tune share sstate. Hash equivalence adds output-based dedup (early cutoff). `bitbake -S printdiff` / `bitbake-diffsigs` explain misses.

### Cited Findings
- Basehash covers "direct inputs into a task"; for shell tasks BitBake generates the run script and checksums it; for Python tasks it "figures out the variable and function dependencies, and then creates a checksum for the data used as the input to the task". Task hash combines basehash with dependent tasks' hashes; exposed as `BB_BASEHASH:task-<name>` and `BB_TASKHASH`. — [Yocto Overview & Concepts](https://docs.yoctoproject.org/overview-manual/concepts.html)
- `BB_BASEHASH_IGNORE_VARS` lists variables "never included in any checksum", including `TMPDIR`, `WORKDIR`, `DL_DIR`, `SSTATE_DIR` (path-dependent variables excluded so different build dirs share sstate). Per-variable control: `PACKAGE_ARCHS[vardepsexclude] = "MACHINE"` / `PACKAGE_ARCHS[vardeps] = "MACHINE"`. — [Yocto Overview & Concepts](https://docs.yoctoproject.org/overview-manual/concepts.html); [BitBake manual: Execution](https://docs.yoctoproject.org/bitbake/dev/bitbake-user-manual/bitbake-user-manual-execution.html)
- `BB_SIGNATURE_HANDLER` default "OEBasicHash" "adds the task hash to the stamp files ... any metadata change will change the task hash, automatically causing the task to be run again." — [BitBake manual: Execution](https://docs.yoctoproject.org/bitbake/dev/bitbake-user-manual/bitbake-user-manual-execution.html)
- Setscene: BitBake calls `BB_HASHCHECK_FUNCTION` with task hashes to find available artifacts, runs `do_<task>_setscene` to restore them, and `BB_SETSCENE_DEPVALID` decides whether dependencies are needed at all (e.g. no need to restore a compiler if the package output is cached). — [BitBake manual: Execution](https://docs.yoctoproject.org/bitbake/dev/bitbake-user-manual/bitbake-user-manual-execution.html)
- Machine/arch scoping: `PACKAGE_ARCH` defines architecture subfolders (e.g. i586 vs qemux86); machine-specific outputs use e.g. `do_deploy[stamp-extra-info] = "${MACHINE_ARCH}"`; sstate can be reused between machines sharing the same `TUNE_PKGARCH`/`PACKAGE_ARCH`. — [Yocto Overview & Concepts](https://docs.yoctoproject.org/dev/overview-manual/concepts.html)
- Debugging: `bitbake -S none` writes signature data to STAMPS_DIR; `-S printdiff` finds the most recent matching signature (e.g. in sstate) and shows where the stamp trees diverge. — [BitBake manual: Execution](https://docs.yoctoproject.org/bitbake/dev/bitbake-user-manual/bitbake-user-manual-execution.html)
- Hash equivalence server: `BB_HASHSERVE` (bind address), `BB_HASHSERVE_UPSTREAM` (pull from upstream); the server "needs to be maintained together with the Shared State cache"; recommended read-only shared servers; securing it is out of scope of the guide. — [Yocto: Hash Equivalence Server](https://docs.yoctoproject.org/dev/dev-manual/hashequivserver.html)
- Concepts: "outhash" (hash of task output) and "unihash" (the unified hash used for equivalent outputs), motivated by changes such as a comment edit that alter the taskhash but not the output. — [Yocto Overview & Concepts (dev)](https://docs.yoctoproject.org/dev/overview-manual/concepts.html) (fetched page was truncated; only the outline was visible)

### Inferences
- The automatic variable-dependency tracking is BitBake's biggest strength and biggest source of surprise: anything referenced is in the key unless excluded. For a JSON DSL, the equivalent is: the key covers the *fully resolved* recipe object (after defaults/inheritance merged), not the source file text, so editing an unrelated field elsewhere doesn't miss, and every field that reaches the build is covered.
- Yocto's tune layering maps directly to the user's need: `x86-64-v3` packages keyed by a `tune`/`pkgarch` string (e.g. `x86_64_v3`), with `MACHINE`-specific things (kernel config, root image) keyed separately. Arch-independent outputs (`allarch`: docs, scripts, firmware blobs) should have no cpu in the key so they're shared.
- Mechanism of hash equivalence (from general knowledge, consistent with the outline above): after a task runs, BitBake computes an outhash over the output (file contents, modes, etc., with paths normalized), reports (taskhash, outhash) to the server; if another taskhash already produced that outhash, both map to the same unihash, and downstream tasks are keyed by unihash, so they hit cache — early cutoff. It only works if outputs are bit-reproducible.

- Exact outhash algorithm (`OEOuthashBasic`, `SSTATE_HASHEQUIV_METHOD`) and `bitbake-diffsigs`/`bitbake-dumpsig` usage text were not retrievable from the fetched pages (truncation); verify in the Yocto dev-manual "Viewing Task Variable Dependencies"/"sstate" sections.

## General: input-addressed vs content-addressed caching, early cutoff, reproducibility prerequisites

### Takeaway
Input-addressed keys (hash of all inputs) are simple and safe if inputs are complete, but any change cascades downstream. Output/content addressing (Nix CA derivations, Yocto unihash, Shake/Bazel per-action content keys) enables early cutoff: if a rebuilt artifact is bit-identical, dependents aren't rebuilt. Early cutoff only pays off when builds are reproducible (SOURCE_DATE_EPOCH, prefix maps, fixed paths).

### Cited Findings
- Nix: content-addressed output paths depend only on the store object, not how it was made; input-addressed paths depend on derivation inputs. Fixed-output: expected hash declared up front, mismatch = failure, builder may use network. Floating CA (experimental `ca-derivations`): address computed after build; builder gets no impure capabilities. A URL change in a fixed-output fetch doesn't change the path, avoiding cascading rebuilds; floating CA derivations must produce identical output regardless of provisional store paths. — [Nix manual: Content-addressing derivation outputs](https://nix.dev/manual/nix/2.28/store/derivation/outputs/content-address)
- Docker docs: fixed `SOURCE_DATE_EPOCH` preserves cache reuse; dynamic values break it each build. — [Docker: Build cache invalidation](https://docs.docker.com/build/cache/invalidation/)
- Build-path independence: `-ffile-prefix-map=OLD=NEW` (GCC >= 8, Clang >= 10) is an alias for both `-fdebug-prefix-map` (debug info) and `-fmacro-prefix-map` (`__FILE__`); a build-path-prefix-map spec is a work in progress. Debian enables via `reproducible=+fixfilepath`. — [reproducible-builds.org: Build path](https://reproducible-builds.org/docs/build-path/)
- Bazel path mapping is a concrete example of making actions path-independent to enable cross-config hits. — [bazel Discussion #22658](https://github.com/bazelbuild/bazel/discussions/22658)

### Inferences
- "Build Systems à la Carte" (Mokhov, Mitchell, Peyton Jones, ICFP 2018) taxonomy, from my knowledge (PDF could not be text-extracted here): rebuilders are dirty-bit (Make), verifying traces (Shake), constructive traces (CloudBuild, Bazel), deep constructive traces (Nix); schedulers topological/restarting/suspending. Deep constructive traces (key = hash of all transitive source inputs) give up early cutoff; constructive traces keyed by *immediate dependency outputs* keep it. A system that keys each package on its dependencies' *output* hashes (not their input hashes) gets early cutoff for free once builds are reproducible — a strong design choice for this project (e.g. a glibc rebuild that yields identical bytes doesn't rebuild userland).
- Recommended hybrid: key = H(recipe, source commit, toolchain output-hash, deps' output-hashes, platform). Store `input_key -> output_hash` (like AC / unihash map) and `output_hash -> artifact` (CAS). This is exactly Bazel AC/CAS + Yocto unihash in one.
- Since the kernel/VM side has a git commit as source identity, SOURCE_DATE_EPOCH should be the pinned commit's committer timestamp (deterministic per input) — never wall-clock.

### Gaps
- SOURCE_DATE_EPOCH spec page fetch failed (socket error); spec details (definition as UNIX timestamp, "last modification of source") are from general knowledge and should be verified at https://reproducible-builds.org/specs/source-date-epoch/.
- Build Systems à la Carte content not verified from the source in this session (PDF unreadable by fetch tool); citation: https://www.microsoft.com/en-us/research/wp-content/uploads/2018/03/build-systems.pdf

## Practical: normalizing inputs, toolchain identity, forbidding nondeterministic inputs

### Takeaway
Hash a canonical, fully resolved JSON document (sorted keys, no defaults left implicit, resolved flags), plus content hashes of sources and toolchain, plus sorted env. Make the toolchain a built, hashed artifact. Reject host-dependent values (`-march=native`, `-mtune=native`, unset SOURCE_DATE_EPOCH, network access, absolute host paths) at validation time.

### Cited Findings
- REAPI requires canonical ordering: env vars sorted by name; platform properties sorted by name then value; case changes alone create new cache entries. — [remote_execution.proto](https://github.com/bazelbuild/remote-apis/blob/main/build/bazel/remote/execution/v2/remote_execution.proto)
- Undeclared host tools/env cause wrong hits or misses (Bazel); path-dependent variables are excluded from signatures (Yocto `BB_BASEHASH_IGNORE_VARS`); mtime ignored for COPY (BuildKit). — [Bazel: Remote Caching](https://bazel.build/remote/caching); [Yocto concepts](https://docs.yoctoproject.org/overview-manual/concepts.html); [Docker cache invalidation](https://docs.docker.com/build/cache/invalidation/)
- Salt field to namespace caches. — [remote_execution.proto](https://github.com/bazelbuild/remote-apis/blob/main/build/bazel/remote/execution/v2/remote_execution.proto)

### Inferences (design recommendations for the JSON DSL)
- Canonicalization: use RFC 8785 JSON Canonicalization Scheme (JCS) or equivalent (sorted keys, no insignificant whitespace, normalized numbers, UTF-8 NFC strings). Merge defaults/inheritance *before* hashing; represent sets (feature lists) as sorted, de-duplicated arrays; keep ordered lists (e.g. patch order, CFLAGS order) as lists. Hash with a domain-separated prefix, e.g. `sha256("pkgkey/v1\0" + jcs(doc))`, and bump `v1` when the hashing scheme changes.
- Key composition (per build node): `{schema_version, recipe (resolved), sources: [{url, commit, tree_hash}], patches: [content hashes], platform: {arch, isa_level, os, libc, abi}, toolchain: output-hash, deps: [output-hashes sorted by name], env: sorted allowlist, builder_image: hash, salt}`. Explicitly *exclude* build dir, job count (`-j`), host name, user, timestamps — Yocto's ignore list pattern; but only exclude a field after confirming it doesn't affect output.
- Platform model: borrow Bazel/Buck2 constraint settings with closed enums: `arch ∈ {x86_64, aarch64}`, `x86_level ∈ {v1,v2,v3,v4}` (only valid when arch=x86_64), `aarch64` levels similarly (e.g. armv8-a, armv8.2-a). Derive compiler flags *from* the platform (`-march=x86-64-v3`), never accept raw `-march` from recipes; this way the key includes the semantic level and flags can't drift. Separate target platform from exec (build-host) platform; include exec platform in key until cross builds are proven bit-identical across hosts.
- Kernel sharing: key the kernel on (linux-libre commit, resolved `.config` content hash after `olddefconfig`, toolchain hash, platform). Hashing the *resolved* `.config` rather than the fragment list means two VMs whose fragments differ but resolve identically share a build (a cheap form of early cutoff at the configuration level).
- Forbid nondeterminism by a validator: reject `-march=native`/`-mtune=native`/`-mcpu=native`, `$(date)`, unpinned branches/tags (require 40-hex commit), network during build (only fixed-output fetch steps with declared hashes, Nix-style), and env vars outside allowlist. Always set `SOURCE_DATE_EPOCH` (commit timestamp), `-ffile-prefix-map=$builddir=.`, `TZ=UTC`, `LC_ALL=C`, fixed umask, sorted tar with `--mtime=@$SOURCE_DATE_EPOCH --owner=0 --group=0 --numeric-owner`.
- Explain misses like `bitbake-diffsigs`: store the full canonical key document (not just its hash) next to each cache entry; `explain <target>` diffs the current key doc against the nearest cached one. Cheap to implement, very valuable for an AI maintainer.
- Verify hermeticity: periodically rebuild a cached entry and compare output hash (Yocto/Nix reproducibility checks); mismatches mark the recipe "non-reproducible" (disable early cutoff for it) rather than silently trusting it.
- Avoid configuration explosion: keep the number of platform dimensions tiny and make arch-independent artifacts (headers, docs, firmware, scripts) declare `platform: "any"` so they are shared (Yocto `allarch`), and don't propagate target-only settings into tools built for the exec platform (Bazel exec config).

### Gaps
- No primary source fetched for RFC 8785 JCS or for GCC `-march=x86-64-v3` level definitions (from GCC 11+ per general knowledge); verify in GCC docs / psABI if needed.
