Documentation / Getting started

Build a machine from one system file.

A system file links a machine profile to a software profile. Eclogite validates both branches, resolves the complete graph, locks every input, and produces either a VM bundle or a physical-machine image.

single JSON input typed references immutable output

01 · Input

The system file

The preferred interface is one strict JSON or JSONC system definition passed with --config. The checked-in UTM example uses aliases for predefined catalog objects:

{
  "schema": "eclogite.system/v1",
  "name": "utm-arm64",
  "machine": "utm-arm64",
  "software": "minimal-arm64"
}

Keep the configuration outside the empty output directory, then run:

mkdir machine && cd machine
eclogite create \
  --config ../examples/utm-arm64.json \
  --fetch
./vm.sh run
Why one file?

The machine and software remain independently reusable, but the system file is the complete reviewed decision about which pair becomes one output.

02 · Resolution

Aliases and file links

Each reference has one deterministic interpretation. Resolution never searches by prefix or downloads an arbitrary URL.

InputMeaningExample
Bare stringExact typed catalog name or declared aliasutm-arm64
./ or ../File relative to the system file../software/base.jsonc
Absolute pathRejected in persisted intent/Users/…
HTTP or Git URLRejected; use a pinned catalog sourcehttps://…

The lock records the canonical object name, defining catalog or file, content hash, and alias provenance. Changing a linked file changes the input hash.

03 · Commands

One selector across the CLI

Validation, inspection, locking, and creation consume the same file:

eclogite validate system.json
eclogite graph --config system.json --format tree
eclogite plan --config system.json
eclogite lock --config system.json
eclogite create --config system.json --fetch

--machine and --software remain available as an interactive shorthand. Scripts and CI should use --config so the complete intent is reviewable.

Detailed source document: docs/cli.md

04 · Data model

Machine and software stay separate

Machine profile

  • Architecture and exact CPU model
  • vCPU count and memory
  • Boot method and firmware
  • Storage, network, and console
  • QEMU, UTM, or physical runtime contract

Software profile

  • Platform and build stages
  • Kernel or operating-system family
  • Packages, services, and init
  • Read-only root policy
  • Image format and tests

Compatibility validation requires both profiles to resolve to the same platform and checks that the machine provides every device capability required by the software.

Detailed source document: docs/configuration.md

05 · Build design

Resolve before executing

system.json
    ↓ validate + resolve
system.lock.json
    ↓ emit deterministic plan
state/plan.mk
    ↓ execute inside pinned build VM
immutable layers
    ↓ compose + test
VM bundle or hardware image

The standalone C host tool owns parsing, schemas, graph resolution, locks, cache keys, and plan generation. GNU Make schedules generic builders. Package JSON is data and never becomes an embedded scripting language.

Detailed source document: docs/architecture.md

06 · Deployment

QEMU and UTM use the same public runner

A virtual output contains immutable artifacts, vm.json, a generated backend driver, and a bundle-local vm.sh. The public lifecycle stays consistent:

./vm.sh validate
./vm.sh run
./vm.sh start
./vm.sh console
./vm.sh status
./vm.sh stop

The UTM ARM64 profile requires Apple Silicon and UTM 5 or newer. It uses UTM's QEMU backend with HVF, direct kernel boot, an imported disk copy, serial console, shared NAT, and VirtFS/9p.

Detailed source document: docs/vm-bundle.md

07 · Local and remote state

Downloads and layers are shared

The single eclogite executable uses per-user storage under ~/.cache/eclogite/ for catalog snapshots, Git mirrors, package sources, and immutable build layers. Projects keep only their intent, locks, plans, and outputs.

Remote layers are accepted only when the input key, immutable digest, manifest hashes, and trusted workflow provenance all match.

Detailed source document: docs/storage.md

08 · Project status

Design first, then migrate package by package

GitHub CI will validate the C tool, schemas, catalog, plans, shell contracts, and generated site on Linux and macOS. Dedicated KVM-capable runners will build and publish signed layers. UTM receives a separate Apple Silicon smoke-test environment.

The current repository remains at the research and layout milestone. No C builder, generic Make builders, operational vm.sh, or GitHub workflows have been implemented yet.

Reference implementation

linux-libre-vm remains independent and buildable throughout migration. Its images, kernel settings, runners, and boot tests are the compatibility oracle.

Detailed source documents: docs/ci.md and docs/migration.md
