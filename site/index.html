Configuration-first · immutable outputs · reproducible builds

Build the whole machine.
Keep the intent.

Eclogite turns reviewed JSON configuration into a complete machine image. Choose hardware, software, and a kernel or operating-system family; it validates the combination, resolves every input, builds it in a controlled environment, and produces an immutable result for a VM or physical device.

Getting started

Choose. Review.
Build once.

Start with short catalog names, or pass your own JSONC files. The shorthand is expanded into recorded intent before locking, so convenience does not create hidden build state.

01 / intent

Write one system file.

Machine and software stay reusable, but one reviewed JSON file links the exact pair you want to build.

{
  "schema": "eclogite.system/v1",
  "name": "utm-arm64",
  "machine": "utm-arm64",
  "software": "minimal-arm64"
}
Browse machine profiles →
02 / references

Use aliases or file links.

Bare names resolve predefined catalog objects. Relative paths resolve from the system file, so the same definition works from any directory.

"machine": "utm-arm64"
"software": "minimal-arm64"

or

"machine": "./my-machine.jsonc"
"software": "../software/base.jsonc"
Read the reference rules →
03 / build

Resolve, review, create.

Every command consumes the same file. The lock records canonical objects and hashes before any builder runs.

eclogite plan \
  --config system.json

eclogite create \
  --config system.json \
  --fetch

One source of truth

The catalog describes.
The plan proves.

Package JSON stays declarative: immutable source revisions, typed dependencies, builder selection, and package-owned resources. eclogite validates that intent and emits a deterministic Make plan.

Build output never leaks back into the catalog. Locks, source trees, and immutable layers can be inspected, compared, discarded, and reconstructed.

01

Resolve before executing

Schema validation, meta-package expansion, cycle detection, platform selection, and input hashing complete before a builder runs.

02

Trust before caching

Git mirrors, source snapshots, and package outputs use immutable identities. Remote layers also require signed build provenance before entering the local cache.

03

Replace, never mutate

Eclogite runs on the host. The produced root and its system software are read-only; changing them means producing and replacing a new tested image.

Reproducible build room

The host coordinates.
The VM builds.

The host compiler is never part of a package build. Eclogite boots one pinned development image, mounts one exact target toolchain read-only, and runs the emitted Make plan offline inside that boundary.

Four checks, or build locally.

  • 01 exact input key

A missing or rejected layer never weakens the policy. It becomes a local offline build inside the same runtime.

Ideas in context

Borrow proven machinery.
Decline accidental complexity.

Eclogite is not a universal package ecosystem or a container runtime. It is a deliberately narrow compiler from reviewed machine intent to a reproducible VM bundle or physical-machine image.

01

Nix

Functional package system
What we borrow

Input-derived identities, fixed source revisions, dependency keys, and a lock that separates human intent from a concrete build.

Eclogite's boundary

JSON is data, not a lazy programming language. One pinned version per package makes resolution a topological sort, with no overlays or fixpoint override APIs.

02

Guix

Scheme-based system manager
What we borrow

Explicit build, target, and runtime input roles; immutable store-like outputs; and the ability to reproduce a system from pinned catalog state.

Eclogite's boundary

No Scheme evaluation, package transformations, grafts, or deep input rewriting. A changed input produces a visible lock and rebuild plan.

03

Docker / BuildKit

Container image pipeline
What we borrow

A dependency DAG, parallel work, immutable cached results, and the convenience of shipping one self-contained runtime artifact.

Eclogite's boundary

The output is a bootable VM or hardware image with its selected kernel—not a host-kernel container. Inputs are graph nodes, not mutable network activity hidden inside RUN.

04

Yocto

Embedded distribution builder
What we borrow

Package groups, feature effects, kernel configuration fragments, task hashing, and tools that explain why a build signature changed.

Eclogite's boundary

No layer priority, .bbappend chains, override syntax, or inline Python. Defaults live in typed builders and package intent remains inspectable JSON.

05

Buildroot

Root filesystem builder
What we borrow

Reusable package infrastructures, per-package directories, kernel fragments, and a whole-system image assembled on the host.

Eclogite's boundary

The catalog is schema-validated data and package outputs receive content-aware input keys, manifests, comparison results, and reusable cache layers.

Design synthesis from the project’s package-build DSL research. The goal is a smaller problem surface, not feature parity with these systems.
